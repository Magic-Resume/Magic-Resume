# AI Lab Native · 设计纲要

> 本文只定方向、状态与约束，不写代码。交给实现时配合 `.impeccable.md` 的 Design Context 一起读。

## 0. 这次重构的前提（已确认）

| 项 | 结论 |
|---|---|
| 范围 | **AI 实验室独立于编辑器**，可以有自己的视觉与动效预算，不必迁就编辑器 chrome |
| AI-Native | 四层全要：生成式界面 · 意图优先 · 过程可见 · 视觉语言 |
| 动效 | **不设上限** |
| 唯一反目标 | **卡顿掉帧** |
| 痛点 | 整体气质普通 · 输入区与技能入口 · 左侧对话区（右侧画布不在其中，别拆） |

⚠️ **动效不设上限这一条，与两份现行文档直接冲突**：`.impeccable.md` 的 Anti-reference 第一条是「花哨空洞的动效」，`specs/ai-working-motion/brief.md` 明确要删掉涟漪、光晕爆炸、假进度、spinner。以本文为准意味着那两份要同步修订，否则后续实现会自我打架。见 §9。

## 1. Feature Summary

AI 实验室是求职者与 Polaris **共同施工一份简历的独立工作台**。这次重构换掉它的底层比喻：从「一个带预览面板的聊天应用」，改成「两方在同一份文档上干活的工作台」——界面由模型按当前任务组装，一切从说一句话开始，AI 的工作过程本身是可看、可查、可回溯的对象。

对象是中文市场的求职者，带着一个明确的目标岗位，在一次几分钟到半小时的专注时段里，把简历推向那个岗位。

## 2. Primary User Action

**说出此刻的目标，然后看着简历朝那个目标变化。**

不是"发一条消息"，也不是"使用某个功能"。每一个设计决策都用一把尺子量：*这一步是否让用户更快看见简历在变？* 让不到的，砍掉。

## 3. Design Direction

延续 Design Context 的深色工作台、sky 点缀、Polaris 人格。这次加三条新的：

### 3.1 一个 Polaris，不是一排头像

现在每条 bot 消息旁挂一个 24px 静态头像，Polaris 被稀释成了列表项目符号——一个本该是角色的东西，退化成了排版元素。

改成**唯一的、常驻的 Polaris**：它有自己的工位，它的姿态就是系统状态。素材已经齐了（`public/marks/` 下 static / thinking / typing / excited 四张姿态，目前只用了三张，且只当头像使）。消息不再各自带头像；只有一个 Polaris，它在看、在想、在写、在等你。

这是整个产品唯一别人抄不走的东西，也是反目标「做成 ChatGPT / Claude / Cursor 的样子」最直接的解药。

### 3.2 重力在中间，不在两边

现在是左栏 + 右栏的对称分割，两边都常驻。改成：**画布是舞台主体，对话是可收放的旁白**，左右配比随当前任务变化——创建/问答类偏左，评审/分析类偏右。用户不需要手动调，任务切换时它自己就位。

### 3.3 动效预算全砸在转场上

不设上限，不等于处处都动。**预算应该集中在"状态真的变了"的瞬间**：进场、模式切换、卡片落定、提案被接受、成稿落地、布局重心迁移。

反过来说，常驻氛围动效（永续飘移的极光、一直转的描边）是这次要**避开**的——它们既会在长时段停留里变成噪音，又恰好是最容易掉帧的一类（大面积 `filter: blur` + `backdrop-filter` 叠层），直接撞上唯一的反目标。

## 4. Layout Strategy

**一块画布，三种重心。** 不是三个页面，是同一个空间在移动。

| 态 | 空间 | 用户看到什么 |
|---|---|---|
| **起手**（空会话） | Polaris 与意图台居中，屏幕上没有别的 | 只有一个问题：你想干什么 |
| **工作中** | 意图台下沉为底座，对话在左，画布在右；宽度按任务给 | 左边是过程，右边是结果，两边同时在动 |
| **评审** | 画布吃满，对话压成窄栏或浮层 | 只剩简历和待定的改动 |

三态之间的过渡是**这次"丝滑"最大的一块杠杆**：用 View Transitions 做共享元素形变（意图台从居中长成底座、卡片形变进画布），而不是各自淡入淡出。`experimental.viewTransition: true` 在 `apps/web/next.config.ts:268` 已经开着，现成。

## 5. Key States

| 状态 | 用户需要看到 | 需要感到 |
|---|---|---|
| 空会话 / 首次 | Polaris + 一个意图台 + 三五个够得着的起点 | 不发憷，知道下一步 |
| 输入中 | 打到一半时相关技能自己浮现（不用先知道 `/`） | 被接住，而不是被要求学语法 |
| 等待首响 | Polaris 换成 thinking 姿态，一行会换词的叙述 | 有人在，事情在推进 |
| Agent 工作中 | 工作条：读了什么、调了什么、走到第几步，可展开细看 | 看得见它在干什么、为什么 |
| 需要输入 | GenUI 卡片，点选为主 | 三秒能答完 |
| 需要许可 | 授权卡，说清要读什么、为什么，可拒绝 | 有掌控感 |
| 提案待评审 | 改动就地标在简历上，红删绿增，逐条可接受/拒绝 | 是提案不是既成事实 |
| 成稿 | 画布成形 + 收尾建议轨 | 有成果，且知道下一步 |
| 出错 / 超时 / 额度不足 | 保留已输入内容 + 一个能继续的选择 | 没白干 |
| 会话恢复 | 过期的卡片明确不可点 | 不会点下去才发现失败 |

## 6. Interaction Model

### 6.1 对话区：两层，不是一条流

现在所有东西挤在一条时间线上——一行灰色的 `log` 和一整张改动提案卡权重相同。拆成两层：

- **回合层**：用户说了什么、Polaris 得出了什么结论。全宽、散文、可读。
- **工作层**：为得出这个结论它做了什么——读简历、调工具、走计划、生成提案。**每一轮折叠成一条"工作条"**，默认收起只显示一行摘要（"读了简历 · 改写了 4 处 · 用时 12s"），点开是结构化的步骤。

这一条同时解决两个痛点：对话区不再是一锅粥，而"过程可见"从灰色噪音升级成一等公民。

### 6.2 意图台：主对象，不是页脚

- 空会话时它居中且大，是屏幕上唯一的东西；开始工作后下沉为底座，**但用形变过渡，不是消失再出现**。
- 技能不再藏在 `/` 菜单里。用户打字时相关技能**就地浮现**为可点的建议；每轮结束后以 chips 形式给出下一步。`/` 保留给熟手，但不再是唯一入口。
- 模式激活时输入框整体换上该技能的色（横幅 + 胶囊 + 描边），让"我现在处于什么模式"在余光里成立。

### 6.3 一条贯穿的原则：改动先提案

沿用 Design Context 原则③。AI 的任何改动都先标在简历上、可拒绝、有理由。这次重构不动这一条，也不动右侧画布的评审流（它不在痛点里）。

## 7. 性能契约

用户的唯一反目标是掉帧，所以这一节和设计同等重要，实现时按条对表：

1. **只动 `transform` / `opacity`。** 绝不动 `width` / `height` / `top` / `left` / `margin` / `padding`。
2. **高度变化用 `grid-template-rows: 0fr ↔ 1fr`**，不用 `height`，也不用 framer-motion 的 `layout`——后者靠 scale 做尺寸动画，缩放期间文字必然发虚（这次会话里已经踩过并修过一次）。
3. **`filter: blur` 与 `backdrop-filter` 一屏最多一处，且不在大面积上**。这两个是掉帧的头号来源。想要氛围，优先用预渲染的径向渐变而不是实时模糊。
4. **流式输出期间，同一合成层上不跑动画。** token 每帧都在改文本，会触发重排；画布必须独立成层。
5. **`will-change` 动画开始时加、结束即摘**，不常驻——常驻会持续占显存。
6. **验收方式**：Performance 面板录一次完整链路（发送 → 首 token → 卡片落定 → 提案接受 → 布局切换），掉帧数为 0。这是硬门槛，不是"感觉流畅"。

## 8. Content Requirements

- **Polaris 语气**：温暖、略俏皮，但俏皮不进建议本体；建议永远具体、诚实。开场可以尽情展现小宠性格。
- **状态叙述**：说用户下一步能做什么，而不是报系统状态。不用内部工具名、服务名。
- **工作条摘要**：一行说清"做了什么 + 结果"，不是"正在执行 step 3/5"。
- **空态**：教会界面怎么用，不是"暂无内容"。
- **错误**：给一个能继续的选择，不暴露堆栈和机器码。
- **中文优先**：文案以简体中文为主，英文跟随；现有 `FORM_DEFS` 仍是硬编码中文，重构时一并收进 i18n。

## 9. Open Questions

1. **规范冲突必须先解。** `.impeccable.md` 的 Anti-reference 与 `specs/ai-working-motion/brief.md` 现在与本文矛盾。建议：保留"不弹跳、不假进度、不 spinner"（这三条与掉帧红线一致），删掉"动效要克制"的表述，改成"预算集中在转场"。不改的话，后续每次实现都要在两套规范之间选边。
2. **三态布局的切换由谁触发？** 自动按技能推断，还是留一个手动开关？自动更丝滑，但用户可能想在评审时继续对话。
3. **Polaris 工位放哪。** 左上角常驻、还是跟着当前工作区域走？后者更有生命力，但容易变成满屏乱跑。
4. **工作条默认收起还是展开？** "过程可见"要求它显眼，但每轮都展开会把对话区重新塞满。
5. **移动端。** 三态布局在窄屏下如何退化——本文按桌面工作台设计，窄屏需要单独一轮。
