---
title: Architecture overview
description: "Magic Resume defines resumes with a shared Zod schema, edits them through JSON Patch, and persists browser data in IndexedDB."
---

A single Zod schema in `@magic-resume-kit/resume-schema` describes the resume shape, which the web app, MCP server, and AI agents all read and write. MCP tools edit resumes through JSON Patch, validated against the schema before storage, and the web editor produces patches too.

Magic Resume is built around four ideas that show up everywhere in the code:

1. **The resume is a typed value.** A single Zod schema in `@magic-resume-kit/resume-schema` describes what a resume is. The web app, the MCP server, and the AI agents all read and write that same shape.
2. **The browser is the database.** In self-hosted mode there is no server-side persistence. IndexedDB (`MagicResumeDB`) is the source of truth. Cloud sync is an optional one-way push to the Core API.
3. **Auth is feature-flagged.** `NEXT_PUBLIC_APP_MODE` chooses at build time whether Clerk middleware and the cloud sync layer are loaded. The same UI runs in both modes.
4. **Edits are patches.** MCP tools mutate resumes via JSON Patch (`fast-json-patch`), validated against the schema before they touch storage. The web editor produces patches too — it's the same code path.

## How does resume data flow?

```
                ┌───────────────┐
   User input ─▶│  Editor (UI)  │
                └───────┬───────┘
                        │ Zustand action
                        ▼
                ┌───────────────┐    write    ┌────────────┐
                │ useResumeStore├────────────▶│ IndexedDB  │
                └───────┬───────┘             └────────────┘
                        │ (cloud mode only)
                        ▼
                ┌───────────────┐    PATCH    ┌────────────┐
                │  httpClient   ├────────────▶│  Core API  │
                └───────────────┘             └────────────┘

   AI tool ────▶ @magic-resume-kit/mcp ──▶ Core API (PAT auth)
```
